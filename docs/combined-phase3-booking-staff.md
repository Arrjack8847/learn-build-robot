# Phase 3 — Booking and staff dashboard
Combined parent UI and staff dashboard share the canonical scheduling repository, J2 ownership and verified J3 membership. Parent overview combines availability/bookings and waitlist at one confirmed repository version; server rechecks ownership and eligibility before changes. Staff snapshot refuses a concurrent change; staff walk-in and attendance use canonical capacity and the booked hour.
Individual private-preview staff access replaces the old shared operator key. COMBINED_STAFF_ROSTER_JSON is an environment-only array of {staffId,name,keyDigest,enabled,permissions}; max 20; staffId starts staff- with 10–64 lowercase letters/numbers/hyphens after prefix. Issue each approved staff tester an independently generated 32-byte random hex key through a secure channel. Store only SHA-256 of the lowercase hex text in the roster. Never commit credentials or actual personal names. Role grants: schedule:read required; optional schedule:walk-in, schedule:attendance (including code issue), schedule:excuse. Missing/invalid roster, disabled identity, duplicate key, mixed session and shared key fallback are rejected. Access key held in browser memory only; every API request revalidates roster. Staff action attribution persists stable individual staff ID, with display name resolved for current roster. Rotation/revocation requires changing the private runtime environment; production account provisioning/SSO not implemented.
No live staff roster configured, no individual accounts provisioned, no activation or deployment. Test credentials must be issued by company owner; tests prepared, execution deferred.
