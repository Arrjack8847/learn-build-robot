# J1234 Phase 05 — attendance and check-in
Development-only, protected preview, approved fictional inboxes, no additional staff login. One explicitly operator-created same-day booking per exact student per MYT date; no live booking calendar, capacity scheduling, deposit or overnight checkout. Existing standalone J4 fixture remains unchanged. New scoped attendance record in existing editor-only SandboxBillingState uses j1234-attendance-v1-<hash(student/date)> and CAS versioning; not shared with billing checkout aggregate. Booking, code, attendance, visit marker and audit committed together. Eight digit cryptographically random codes, HMAC scoped to student+booking+codeId, five minutes, maximum three wrong attempts per issued code, max three issues per 15 minutes and 24/day; reissue supersedes prior code; no plaintext persisted or returned on replay. Exact student session required to redeem, server derives studentId; current consent, registration, isolated PIN and active verified membership checked before booking/issue/redeem and rechecked immediately before CAS. Concurrent redemption only one winner. Staff no-show/excuse/revoke/checkout do not grant membership. Check-in and checkout establish attendance only; visit marker is NOT J5 learning access. UI staff controls and student form use same-origin bounded endpoints; directory shows current-day attendance. Explicit J1234_ATTENDANCE_ENABLED and J1234_ATTENDANCE_OPERATOR_ENABLED gates, unset. Staff operator endpoint additionally refuses student/payer cookies; this is not a real role boundary, and protected-preview access plus approved fictional data is mandatory. Actual trusted staff identity required before any real record or multi-user rollout. Membership and attendance use different CAS rows; an adverse event can land after the final membership read, therefore future access must independently recheck current membership and visit state. No actual database mutation, provider request, real student data, production changes or J5 work. Live acceptance deferred, including runtime Wix CAS and deployment. Test setup uses injected fixtures.
