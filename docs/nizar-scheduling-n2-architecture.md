Date: 2026-11-27. N1 decisions: docs/nizar-scheduling-n1-n2-20261127.md.

## Native Wix Bookings evaluation
Official docs: [Create Booking](https://dev.wix.com/docs/api-reference/business-solutions/bookings/bookings/bookings-writer-v2/create-booking), [Reschedule Booking](https://dev.wix.com/docs/api-reference/business-solutions/bookings/bookings/bookings-writer-v2/reschedule-booking), [Sample Flows](https://dev.wix.com/docs/api-reference/business-solutions/bookings/bookings/bookings-writer-v2/sample-flows). Classes support event-based availability and creation with capacity checks; rescheduling a class is limited to sessions of that same class. Native booking alone does not establish atomic enforcement of one child/day across both classes, seven upcoming bookings, HitPay eligibility and deposit state. No claim that native Wix cannot support these via additional infrastructure. Live native class proof not performed.

## Selected private development design
Use Wix CMS as the single canonical booking store in the private pilot, custom React interface in N3, and existing conditional Wix REST update adapter. [Update Data Item](https://dev.wix.com/docs/api-reference/business-solutions/cms/data-items/update-data-item) documents update conditions. Existing adapter uses consistent reads, conditional replacement and explicit conflict outcomes. Never use separate native booking inventory in parallel. This decision is provisional for development; owner/provider approval and production scalability proof remain pending.

Private collection provisioned: NizarSchedulingPreview. Administrator/CMS-editor restricted read/write; server key restricted to approved dev site. Single record nizar-scheduling-preview-v1: environment, stateVersion, stateJson. Initial state empty only if no record; bounded 1000 booking rows and 200000 bytes (conservative code limits, not Wix limits). One aggregate permits CAS across days/activity pools; no automatic pruning or archive. This is a bounded pilot, not scalable production storage. Must design safe retention/partitioning or transactional provider before exceeding bounds. Empty collection created on the existing development site; no booking data inserted. No direct public access or UI endpoint is implemented.

Files: scripts/nizar/policy.mjs (N1 rules, exact MYT clock, 7 calendar-day inclusive horizon); contract.mjs (canonical booking and safe parent/attendance projections); repository.mjs (validate capacity/day invariants and bounded atomic replacement, conflict/unconfirmed). Seven-upcoming rule is now additionally guarded at write time. Membership, idempotent booking commands, authorization, scheduling changes, waitlist reservations and deposit ledger belong to N3/N4. N3 must re-evaluate all rules on each CAS retry; no mutation on unconfirmed response without idempotency read. N4/5 must integrate into same authority rather than split into competing records. Booking state and external membership are not one transaction; fresh verification and denial on uncertainty required. Parent/canonical child resolver to reuse J2, J3 verified ledger, J4/J5 attendance commit; no second sign-in. Live integration branch not modified. 
NIZAR_SCHEDULING_ENABLED defaults off; exact branch scope; no server endpoint or automatic deployment. Wix development collection provisioned and schema/permission readback recorded in the N2 provisioning report. No native booking trial or actual booking/provider test run. Fixture tests registered for later Codespaces run. N2 source and collection preparation complete; real adapter access, permission-denial test, concurrency proof and owner/company agreement still pending.
